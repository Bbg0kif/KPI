# DEFENSE — Завдання 5: Архітектура

## 1. Намір і критерії

Побудувати компонентну модель каталогу відеоігор та особистої
бібліотеки, яка показує модулі, їхні інтерфейси, залежності
й межу системи. Критерії прийняття: кожен інтерфейс має
визначеного постачальника та споживача, а відповідальність
компонентів узгоджена з попередніми лабораторними.

## 2. Топ-3 розбіжності та виправлення

### 1. Конфлікт ідентифікаторів у PlantUML

У початковому описі пакет API та компонент BackendAPI
використовували однаковий ідентифікатор API.
Через це PlantUML не міг побудувати діаграму.

Для пакета задано окремий псевдонім ApiLayer.
Після виправлення діаграма відображається.

Виправлення входить до коміту:
`Add component diagram with interfaces and system boundary`.

Помилку виявлено під час побудови початкового рендера;
окремого коміту з непрацездатною версією немає.

### 2. Недостатньо визначений результат отримання гри

У переліку операцій GameRepository був метод findById(gameId),
але не було явно описано, чи повертає він жанри гри.
Водночас R5 і SC10 з Lab2 передбачають показ жанрів
у відомостях про гру.

У spec.md уточнено: findById повертає гру разом із її жанрами
або null, якщо гри немає. Також зазначено, що listGenres
повертає і жанри без ігор, щоб підтримати SC09.

Коміт-виправлення:
`Clarify repository results and data contracts`.

### 3. Недостатньо визначені результати операцій репозиторіїв

Не було чітко описано результати пошуку відсутнього запису,
повторного створення, зміни та видалення запису бібліотеки.

У spec.md уточнено:
- пошук одного відсутнього запису повертає null;
- пошук списку без результатів повертає порожній список;
- конфлікт унікальної пари користувача та гри передається сервісу;
- зміна статусу не змінює added_at;
- видалення стосується лише запису бібліотеки;
- технічна помилка БД не прирівнюється до відсутності даних.

LibraryService визначає результат бізнес-операції,
а інтерфейс показує відповідне повідомлення користувачу.

Коміт-виправлення:
`Clarify repository results and data contracts`.

## 3. Ключове рішення — альтернативи та вибір (ADR)

Ключове рішення — організувати Backend як один застосунок
із внутрішніми модулями API, сервісів і доступу до даних.

Розглянуті альтернативи:

1. Об’єднати обробку запитів, бізнес-правила та SQL
   в одному компоненті.

   Такий варіант має менше компонентів, але змішує різні
   обов’язки. Складніше простежити, де перевіряється доступ,
   де виконується додавання гри та де зберігаються дані.

2. Створити окремі мікросервіси каталогу, бібліотеки
   та автентифікації.

   Це дозволило б розгортати їх незалежно, але потребувало б
   мережевої взаємодії та обробки збоїв між сервісами.
   У вимогах немає потреби в такому незалежному розгортанні,
   тому для цієї моделі це зайве ускладнення.

3. Залишити один Backend, але розділити його на модулі
   з визначеними інтерфейсами.

   Обрано цей варіант. BackendAPI приймає запити,
   сервіси виконують бізнес-правила, а репозиторії
   відповідають за доступ до даних.

LibraryService зберігає відповідальність за перевірку доступу
та операції з бібліотекою, як у Lab3 і Lab4.
CatalogService відповідає за каталог, а AuthService —
за вхід через зовнішній IdentityProvider.

Наслідок рішення: обов’язки компонентів розділені,
але вони залишаються частинами одного застосунку.
Внутрішні інтерфейси не означають окремі HTTP-сервіси.

## 4. Перевірка узгодженості з попередніми моделями

### Lab1 — модель даних

Зіставлено компоненти доступу до даних із сутностями:

- UserRepository — USER.
- GameRepository — GAME, GENRE та зв’язок між ними.
- LibraryEntryRepository — LIBRARY_ENTRY.
- Database — зберігання цих даних і забезпечення обмежень.

Збережено складений ключ LIBRARY_ENTRY:
(user_id, game_id). Він не дозволяє створити два записи
для однієї гри в бібліотеці одного користувача.

Компоненти та інтерфейси не є новими сутностями ER-моделі.

### Lab2 — вимоги та сценарії

Зіставлено відповідальність компонентів із вимогами:

- R1–R5 — WebUI, BackendAPI, CatalogService і GameRepository.
- R6–R8 — AuthService, UserRepository та IdentityProvider
  за участю WebUI і BackendAPI.
- R9–R10 — перевірений контекст сеансу та перевірки
  авторизації і власника бібліотеки в LibraryService.
- R11–R18 — LibraryService і відповідні репозиторії.

Перевірка доступу передує зверненню до даних бібліотеки.
Для зміни статусу перевірка наявності запису передує
перевірці допустимості нового статусу.

Вимога R19 стосується швидкодії. Компонентна діаграма
показує компоненти, що беруть участь у пошуку, але
не підтверджує виконання цієї вимоги.
Для цього після реалізації потрібен навантажувальний тест.

### Lab3 — взаємодія

Збережено LibraryService, GameRepository
і LibraryEntryRepository та їхні обов’язки.

BackendAPI деталізує приймання запитів між інтерфейсом
і сервісами, яке в sequence-діаграмах було спрощено.
AuthService пояснює отримання перевіреного контексту сеансу.

LibraryService отримує ідентифікатор поточного користувача
з перевіреного контексту. Переданий ownerId сам по собі
не підтверджує право доступу.

Під час додавання гри LibraryService не виконує
повторний вхід через IdentityProvider.

### Lab4 — процес

Збережено порядок перевірок процесу додавання:

1. Авторизація користувача.
2. Належність бібліотеки користувачу.
3. Наявність гри.
4. Наявність запису бібліотеки.
5. Створення запису, якщо всі умови виконані.

Підготовка статусу planned та отримання часу T
залишаються внутрішніми діями LibraryService.
Для них не створено окремих компонентів.

Результат операції передається через BackendAPI до WebUI.
Інтерфейс повідомляє користувача; підтвердження отримання
цього повідомлення не потрібне для завершення операції.

### Межа системи та інтерфейси

WebUI, Backend, репозиторії та Database розташовані
в межах системи. IdentityProvider є зовнішньою системою.

Для кожного інтерфейсу зіставлено компонент,
який його надає, і компоненти, які його потребують.
WebUI не звертається до Database напряму.

Перевірка виконана шляхом зіставлення описів та діаграм.
Вона підтверджує узгодженість моделей, а не працездатність
ще не реалізованої системи.

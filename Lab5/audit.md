# Аудит архітектури

## Що перевірено

Зіставлено spec.md, model.puml і зображення діаграми
з попередніми моделями:

- Lab1 — сутності та зв’язки даних;
- Lab2 — вимоги та сценарії;
- Lab3 — взаємодія під час додавання гри;
- Lab4 — процес додавання гри.

Перевірено межу системи, відповідальність компонентів,
постачальників і споживачів інтерфейсів
та обґрунтування залежностей.

## Топ-3 недоліки та виправлення

### 1. Конфлікт ідентифікатора API

**Було:** група package "API" та компонент
BackendAPI з псевдонімом API отримували
однаковий ідентифікатор.

PlantUML повідомляв про повторне визначення елемента
та не будував діаграму.

**Виправлено:** групі призначено окремий псевдонім
ApiLayer. Компонент BackendAPI зберіг псевдонім API.

**Коміт:**
`Add component diagram with interfaces and system boundary`.

Виправлення включено до першого коміту діаграми.
Чернетка з помилкою окремо не комітилася.

### 2. Не визначено склад результату пошуку гри

**Було:** IGameRepository містив findById(gameId),
але не було явно зазначено, чи повертаються жанри.
Водночас R5 і SC10 із Lab2 передбачають
показ жанрів у відомостях про гру.

**Уточнено:** findById() повертає дані гри
разом із її жанрами або null, якщо гри немає.
Жанри отримуються через зв’язок GAME з GENRE.

Також визначено, що listGenres() повертає
і жанри без ігор, потрібні для сценарію SC09.

**Коміт:** `Clarify repository results and data contracts`.

### 3. Не визначено результати операцій репозиторіїв

**Було:** операції пошуку, створення, зміни
та видалення були перелічені, але їхні результати
для відсутніх записів і конфлікту унікальності
не були явно описані.

**Уточнено:**
- пошук одного запису повертає запис або null;
- пошук списку може повернути порожній список;
- створення повертає новий запис або повідомляє
  про конфлікт унікальності;
- зміна та видалення повідомляють про успіх
  або відсутність запису;
- зміна статусу зберігає added_at;
- технічні помилки не прирівнюються
  до відсутності даних.

LibraryService перетворює конфлікт унікальності
на duplicateEntry(). Повідомлення користувачу
формується через API та UI.

**Коміт:** `Clarify repository results and data contracts`.

## Трасування компонентів

| Компонент | Основа в попередніх моделях |
| --- | --- |
| WebUI | Дії та результати сценаріїв Lab2; учасник «Інтерфейс» у Lab3 і Lab4. |
| BackendAPI | Архітектурна деталізація передавання запитів від UI до сервісів. Окремо не показувався у Lab3 і Lab4. |
| CatalogService | R1–R5: каталог, пошук, жанровий фільтр і відомості про гру. |
| LibraryService | R9–R18; перевірки й операції з бібліотекою у Lab3 і Lab4. |
| AuthService | R6–R8: зовнішній вхід; підготовка перевіреного контексту сеансу для Lab3 і Lab4. |
| GameRepository | GAME, GENRE та їхній зв’язок із Lab1; пошук гри у Lab3 і Lab4. |
| LibraryEntryRepository | LIBRARY_ENTRY із Lab1; операції бібліотеки з Lab2 та додавання з Lab3 і Lab4. |
| UserRepository | USER із Lab1; пошук наявного користувача за підтвердженим email у вимогах Lab2. |
| Database | Зберігання сутностей, ключів і зв’язків Lab1. |
| IdentityProvider | Зовнішній актор автентифікації з Lab2. |

Нові компоненти BackendAPI, CatalogService,
AuthService і UserRepository деталізують
розподіл відповідальності в Lab5.
Вони не додають нових можливостей користувачу.

## Перевірка інтерфейсів і залежностей

| Інтерфейс | Надає | Потребує | Призначення залежності |
| --- | --- | --- | --- |
| IApplicationAPI | BackendAPI | WebUI | Передавання запитів і результатів операцій Lab2. |
| ICatalog | CatalogService | BackendAPI | Операції каталогу за R1–R5. |
| ILibrary | LibraryService | BackendAPI | Операції бібліотеки та перевірка доступу за R9–R18. |
| IAuthentication | AuthService | BackendAPI | Вхід за R6–R8 і отримання перевіреного контексту сеансу. |
| IGameRepository | GameRepository | CatalogService, LibraryService | Читання каталогу й жанрів; перевірка гри під час додавання. |
| ILibraryEntryRepository | LibraryEntryRepository | LibraryService | Читання та зміна записів бібліотеки. |
| IUserRepository | UserRepository | AuthService | Зіставлення підтвердженого email з наявним USER. |
| ISqlDataAccess | Database | GameRepository, LibraryEntryRepository, UserRepository | Доступ до даних моделі Lab1 через SQL і транзакції. |
| IExternalIdentity | IdentityProvider | AuthService | Зовнішня перевірка особи за вимогами Lab2. |

Для кожного інтерфейсу визначено постачальника
та щонайменше одного споживача.

Пунктирні стрілки спрямовані від споживачів
до потрібних інтерфейсів.
Суцільні лінії з’єднують інтерфейси
з компонентами, які їх надають.

Зв’язок користувача з WebUI позначає взаємодію
з інтерфейсом користувача, а не програмну залежність.

## Межа системи

WebUI, Backend і Database розташовані
всередині межі системи.

IdentityProvider розташований поза нею.
Він надає результат автентифікації,
але не звертається до нашої Database.

Database розташована поза групою Backend,
але залишається частиною системи.

Групи API, «Сервіси» та Data Access показують
внутрішні модулі одного Backend.
Окремі мережеві сервіси для них не передбачені.

## Узгодженість із Lab1

- GameRepository працює з GAME, GENRE та їхнім зв’язком.
- UserRepository знаходить USER за email.
- LibraryEntryRepository працює з LIBRARY_ENTRY.
- Ключ LIBRARY_ENTRY залишається складеним:
  (user_id, game_id).
- Під час додавання задаються status = planned
  і поточний added_at.
- Зміна статусу не змінює added_at.
- Видалення запису бібліотеки не видаляє GAME.
- Сервіси та інтерфейси не є новими сутностями даних.

Технічний стан сеансу не деталізується
як нова предметна сутність.

## Узгодженість із Lab2

Архітектура підтримує каталог, пошук,
фільтрування, перегляд гри, зовнішній вхід
і керування власною бібліотекою.

Реєстрація, платежі, відгуки та редагування каталогу
не додаються.

Під час входу підтверджений email зіставляється
з наявним USER. Невідомий користувач або невдалий
результат автентифікації не отримує доступу.

Під час зміни статусу перевіряються:
1. право доступу;
2. наявність запису;
3. допустимість статусу.

Це зберігає пріоритет відповіді
«Запис не знайдено» з R18.

R19 стосується продуктивності пошуку.
Архітектурна модель визначає відповідальні компоненти,
але не підтверджує виконання цієї вимоги.
Потрібен навантажувальний тест реалізованої системи.

## Узгодженість із Lab3 і Lab4

Збережено компоненти LibraryService,
GameRepository та LibraryEntryRepository.

Порядок додавання залишається таким:
- перевірка авторизації;
- перевірка власника;
- перевірка наявності гри;
- перевірка запису бібліотеки;
- підготовка статусу та часу;
- створення запису;
- повернення результату користувачу.

BackendAPI деталізує передавання запиту
між UI і сервісами.
Цей компонент був опущений на поведінкових
діаграмах попередніх лабораторних.

AuthService пояснює походження перевіреного
sessionContext. LibraryService використовує його
та не звертається до IdentityProvider
під час кожного додавання.

Паралельна підготовка planned і T з Lab4
залишається внутрішньою поведінкою LibraryService.
Окремих компонентів для цих дій не потрібно.

Повідомлення показує WebUI.
Окремого email/SMS-сервісу немає,
підтвердження прочитання не очікується.

## Межі перевірки

Проведено ручне зіставлення специфікації,
компонентної діаграми та попередніх моделей.

Компонентна діаграма показує структуру й залежності.
Вона не доводить правильність реалізації перевірок,
транзакцій або обробки помилок.

Конкретний протокол зовнішньої автентифікації,
спосіб зберігання сеансу та СУБД не обрані.

Програмний код системи та робота реальної бази даних
у цій лабораторній не перевірялися.
